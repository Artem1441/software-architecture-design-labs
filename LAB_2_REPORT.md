## Краткое описание системы

На платформе ПроБои уже реализована подача заявок на соревнования. В этой работе проектируется следующий этап турнирного модуля: жеребьёвка, корректировка и публикация сеток, проведение поединков, фиксация результатов и выпуск протоколов. Существующие заявки входят в общую модель турнира и используются как исходные данные для допуска и жеребьёвки. Отдельная ML-аналитика на Python относится к будущему этапу и пока не реализована.

Серверная часть развивается на **Node.js, TypeScript и Express.js**, данные хранятся в **PostgreSQL** и **S3-совместимом хранилище**, приложения развёртываются с **Docker**. Для доставки фоновых заданий и результатов используется **RabbitMQ**. Диаграммы показывают целевое устройство модуля: существующие функции заявок и проектируемые функции проведения турнира.

### Обозначения связей

Каждая стрелка имеет одно направление и подпись действия. У межконтейнерных связей указан протокол, у внутренних – вызов функции, callback или сообщение рабочего потока.

| Обозначение | Значение |
|---|---|
| Сплошная синяя стрелка с заполненным наконечником | Вызов функции или запрос. Начало – вызывающий компонент, конец – получатель вызова. |
| Пунктирная синяя стрелка с открытым наконечником | Возврат ответа на конкретный вызов: результат проверки правил, HTTP-ответ или данные запроса. |
| Сплошная бирюзовая стрелка с открытым наконечником | Асинхронное сообщение. Подпись различает команду, результат задания и сообщение между потоками. |

Стрелка от RabbitMQ к исполнителю показывает доставку сообщения. Соединение с брокером устанавливает приложение-потребитель. Пересечение линий без узла не означает связи. Будущая интеграция отмечена словом "планируется".

## 1. Диаграмма системного контекста

На уровне C4-L1 турнирный модуль представлен одной системой. Вокруг него показаны шесть человеческих ролей из первой лабораторной, основная платформа ПроБои и будущая аналитическая подсистема. Внутренние приложения и хранилища раскрываются на следующем уровне.

![C4 L1. Системный контекст турнирного модуля ПроБои](Lab%20Work%20%E2%84%962/docs/img/C4_context.png)

### Описание элементов

| Элемент | Тип | Назначение |
|---|---|---|
| Турнирный модуль ПроБои | System | Связывает заявки и допуск с сетками, поединками, результатами и протоколами. |
| **SH-01 Организатор / представитель федерации** | Person | Настраивает турнир, запускает разрешённые операции подготовки, публикует сетки и получает документы. |
| **SH-02 Судья / секретарь** | Person | Проверяет допуск, работает с сетками и результатами в пределах назначения на турнир. Права судьи и секретаря различаются. |
| **SH-03 Представитель клуба / тренер** | Person | Подаёт заявки своих спортсменов, проверяет их статусы, просматривает сетки и результаты. |
| **SH-04 Спортсмен / законный представитель** | Person | Подаёт доступную ему заявку и получает сведения о допуске и участии. Связь представительства проверяется. |
| **SH-05 Зритель** | Person | Просматривает опубликованные сетки и подтверждённые результаты. |
| **SH-06 Технический администратор** | Person | Использует служебный журнал для разбора инцидентов. Техническая роль не даёт судейских полномочий. |
| **SH-07 Основная платформа ПроБои** | External System | Предоставляет идентификацию, единые профили, реестры клубов и подтверждённые связи. |
| **SH-08 ML-аналитика, планируется** | External System | Будущий получатель разрешённых турнирных данных для анализа. Соответствует необязательной интеграции FR-13. |

### Внешние интеграции

| Внешняя система | Протокол | Назначение |
|---|---|---|
| Основная платформа ПроБои | HTTPS / REST | Проверка идентичности и получение профилей, реестров и связей. Сохраняются единые `athlete_id` и внутренние `club_id`. |
| Будущая ML-аналитика | HTTPS / REST, JSON | Передача разрешённой выгрузки с идентификатором турнира и версией данных. Интеграция подключается после реализации основных турнирных функций. |

Граница системы проходит вокруг турнирного модуля. Поэтому основная платформа является внешней зависимостью, хотя принадлежит тому же продукту. Подача заявок остаётся существующей функцией модуля; сервис жеребьёвки входит в его проектируемую серверную часть.

## 2. Диаграмма контейнеров

На уровне C4-L2 выделены семь контейнеров: веб-клиент, API, два исполнителя, два хранилища и брокер сообщений. Все шесть человеческих ролей связаны с C01. API инициирует фоновые задания через C07, исполнители получают их из своих очередей и передают результаты через брокер обратно в API.

![C4 L2. Контейнеры турнирного модуля ПроБои](Lab%20Work%20%E2%84%962/docs/img/C4_containers.png)

### Описание контейнеров

| Контейнер | Тип | Технология | Назначение | Какие FR покрывает |
|---|---|---|---|---|
| **C01 Веб-клиент** | Container: SPA | TypeScript, React / Next.js, статический клиент | Формы заявок, экраны сеток, результатов, статусов операций и документов. | Пользовательские сценарии FR-01–FR-13. |
| **C02 Турнирный API** | Container: API | Node.js, TypeScript, Express.js, Docker | Проверка прав, заявки, допуск, официальные версии сеток, результаты, задания, аудит и метаданные документов. | FR-01–FR-13. |
| **C03 Сервис жеребьёвки** | Container: Worker | Node.js, TypeScript, worker_threads, amqplib, Docker | Расчёт проекта сетки по неизменяемому входному снимку, публикация результата задания. | FR-05; NFR-01, NFR-02. |
| **C04 Исполнитель экспорта** | Container: Worker | Node.js, TypeScript, PDFKit, ExcelJS, worker_threads, amqplib, Docker | Формирование PDF и XLSX, загрузка в S3, публикация описания пакета; будущие аналитические выгрузки. | FR-11, FR-13. |
| **C05 Турнирная БД** | Container: Database | PostgreSQL | Заявки, допуск, сетки, результаты, версии, права, аудит, задания, снимки, таблица исходящих сообщений outbox и учёт обработанных событий. | Хранение и целостность данных FR-01–FR-13. |
| **C06 Хранилище документов** | Container: Object Storage | S3-совместимое хранилище, S3 API, версионирование | Закрытые PDF и XLSX. Описание пакета фиксирует ключи, версии и контрольные суммы файлов. | FR-11. |
| **C07 Брокер сообщений** | Container: Message Broker | RabbitMQ, AMQP 0-9-1 поверх TLS, Docker | Доставка заданий жеребьёвки и экспорта, доставка сообщений о завершении или ошибке. | FR-05, FR-11, FR-13. |

Только C02 обращается к турнирным таблицам PostgreSQL. Для БД выбран `node-postgres`, для S3 – AWS SDK for JavaScript с согласованным S3-совместимым endpoint. Версионирование объектов является требованием к бакету документов.

Python предусмотрен только для будущей внешней ML-подсистемы SH-08. Жеребьёвка использует алгоритм проверки и оптимизации ограничений на TypeScript.

### Связи между контейнерами

| Откуда | Куда | Протокол | Действие |
|---|---|---|---|
| SH-01–SH-06 | C01 | Браузер / HTTPS | Работа через интерфейс согласно роли. Каждый актор имеет собственную связь с веб-клиентом. |
| C01 | C02 | HTTPS / REST, JSON | Пользовательские команды, запросы данных, статусов и документов. |
| C02 | C01 | HTTP-ответ | Данные, подтверждение команды, статус операции или разрешённый файл. |
| C02 | C05 | PostgreSQL protocol / SQL поверх TLS | Чтение и транзакционное сохранение турнирных данных, заданий, outbox и аудита. |
| C05 | C02 | Ответ PostgreSQL | Данные запроса и результат транзакции. |
| C02 | C07 | AMQP / TLS | Публикация `DrawRequested` и `ExportRequested` из сохранённого outbox. |
| C07 | C03 | AMQP / TLS | Доставка `DrawRequested` из `draw.tasks`. |
| C07 | C04 | AMQP / TLS | Доставка `ExportRequested` из `export.tasks`. |
| C03 | C07 | AMQP / TLS | Публикация `DrawCompleted` или `JobFailed`. |
| C04 | C07 | AMQP / TLS | Публикация `ExportCompleted` или `JobFailed`. |
| C07 | C02 | AMQP / TLS | Доставка событий из `job.results` обработчику результатов API. |
| C04 | C06 | HTTPS / S3 API | Загрузка версий PDF и XLSX. |
| C02 | C06 | HTTPS / S3 API | Проверка пакета и чтение конкретной версии документа. |
| C02 | SH-07 | HTTPS / REST | Проверка идентичности, профили, реестры и подтверждённые связи. |
| C04 | SH-08 | HTTPS / REST, JSON | Будущая необязательная передача разрешённых данных для ML-анализа. |

У S3 и основной платформы ответы возвращаются вызывающему приложению. Запросы пользователя входят через Express Router, сообщения исполнителей – через отдельный AMQP-потребитель результатов. Исполнители не запрашивают новые задания у HTTP API.

### Выбор архитектурного стиля

Выбрана **клиент-серверная сервисная архитектура с асинхронным обменом через брокер и слоями внутри API**. Сервисы жеребьёвки и экспорта развёртываются отдельно, чтобы выделять ресурсы для NFR-01 и NFR-03 и сохранять отзывчивость интерфейса по NFR-04. API остаётся владельцем официальных данных и проверяет правила и полномочия по NFR-02 и NFR-05. Выполнение всех операций в одном процессе отклонено из-за конкуренции за процессорное время, а отдельный микросервис для каждой предметной функции – из-за усложнения согласованных изменений и эксплуатации. RabbitMQ обеспечивает независимую доставку фоновой работы, при этом его введение требует outbox, обработки повторов и контроля общего срока задания.

### Сообщения и данные

| Основная очередь | Сообщения | Содержимое |
|---|---|---|
| `draw.tasks` | `DrawRequested` | `job_id`, турнир, категория или набор категорий, исходная версия, неизменяемый снимок участников и правил, версия алгоритма, `seed`, бюджет итераций и срок. |
| `export.tasks` | `ExportRequested` | `job_id`, вид пакета документов, версия данных, снимок подтверждённых результатов, версия шаблонов и параметры срока. |
| `job.results` | `DrawCompleted`, `ExportCompleted`, `JobFailed` | `event_id`, `job_id`, тип задания, исходная версия и хеш входа; проект сетки, описание файлов либо структурированная ошибка. |

Снимок жеребьёвки и проект сетки передаются в JSON. Бинарные PDF и XLSX передаются через S3; в сообщение попадают ключи, `VersionID` и контрольные суммы. В сообщениях используется только необходимый набор полей. Размер сериализованных данных для нагрузки до 10 000 участников проверяется до внедрения; лимит сообщений RabbitMQ и ограничения валидаторов согласуются с этим размером.

### Путь задания и результата

Дополнительная диаграмма последовательности показывает один сценарий жеребьёвки и порядок взаимодействий между контейнерами.

![Последовательность запроса жеребьёвки и получения результата](Lab%20Work%20%E2%84%962/docs/img/C4_Draw_flow.png)

1. Организатор запускает расчёт в веб-клиенте. API проверяет полномочия и состояние категории.
2. API одной транзакцией сохраняет снимок, задание, аудит и запись outbox. Клиент получает `202 Accepted` и `job_id`.
3. Публикатор API читает сохранённую запись outbox и отправляет `DrawRequested` в RabbitMQ. После подтверждения публикации отмечает запись отправленной.
4. Брокер доставляет сообщение сервису жеребьёвки. Исполнитель проверяет срок и входные данные, затем рассчитывает проект.
5. Исполнитель публикует `DrawCompleted` с проектом либо `JobFailed`. Только после подтверждения публикации исхода он подтверждает обработку исходного задания.
6. API получает событие результата, проверяет его структуру, задание, хеш входа, версию и ограничения сетки.
7. В короткой завершающей транзакции API повторно проверяет актуальность задания, версию данных и предельный срок жеребьёвки, сохраняет проект, завершение задания, идентификатор обработанного события и аудит. Затем подтверждает обработку сообщения результата.
8. При запросе статуса клиент получает готовый проект. Корректировка, утверждение и публикация сетки остаются отдельными действиями FR-06 и FR-07.

Outbox – таблица исходящих сообщений в PostgreSQL. Изменение турнира и запись в неё фиксируются одной SQL-транзакцией; публикация в RabbitMQ происходит после коммита. Если API остановится между подтверждением публикации и отметкой отправки, сообщение может прийти повторно, поэтому получатели учитывают идентификаторы событий и заданий.

Подтверждение публикации означает, что сообщение принято брокером. Подтверждение потребителя означает, что конкретное сообщение обработано. Окончательная готовность сетки определяется записью результата в PostgreSQL.

### Протоколы и сроки

При завершении турнира C02 проверяет наличие всех обязательных результатов и итоговых мест. В одной транзакции сохраняются итоговое состояние, снимок, аудит, задание экспорта и outbox. C04 получает `ExportRequested`, создаёт полный пакет PDF и XLSX по одному снимку, загружает его в S3 и публикует `ExportCompleted`.

API проверяет комплектность пакета и точные версии объектов S3 до завершающей транзакции. В транзакции он повторно проверяет состояние задания и версию данных, затем атомарно сохраняет описание пакета, готовность задания, обработанное событие и аудит. Ключи включают `job_id`, версию данных и хеш содержимого; чтение выполняется по принятому `VersionID`. Исполнитель не получает право удалять принятые версии. Пакет старой версии сохраняется как исторический и не подменяет текущий.

Срок 300 секунд включает outbox, очередь, расчёт, доставку результата, перепроверку и сохранение. Для заказанного набора категорий действует общий срок от принятия запроса. Пять секунд на документы отсчитываются от фиксации завершения турнира до готовности всех файлов, включая outbox, очередь, генерацию, загрузку и обработку события результата. Эти показатели являются целями испытаний; добавление брокера само по себе не подтверждает их достижение.

Предельный срок жеребьёвки хранится в задании и проверяется API и исполнителем. Время жизни сообщения в очереди не заменяет этот контроль. Для документов отдельно фиксируются целевое время готовности и технический тайм-аут: поздний пакет может быть принят, но превышение пяти секунд означает невыполнение NFR-03.

Очередь `export.tasks` предназначена для документов. Для будущей аналитики предусматривается отдельная `analytics.tasks` с собственным потребителем и независимым ограничением неподтверждённых сообщений в том же C04. Аналитика использует отдельные вычислительные слоты, поэтому не занимает доставку и ресурсы, зарезервированные для протоколов.

### Развёртывание и доставка

API, жеребьёвка и экспорт имеют отдельные Docker-образы. RabbitMQ развёртывается отдельно; PostgreSQL и брокер используют постоянное хранение. S3 подключается по endpoint. Для разработки состав сервисов можно запускать через Docker Compose.

Очереди и сообщения сохраняются на диске. Используются подтверждения публикации, проверка маршрутизации и ручное подтверждение обработки сообщений. Число неподтверждённых заданий ограничивается свободными вычислительными слотами исполнителя. Повторы транспортных ошибок ограничены политикой повторов и сроком задания; необработанное сообщение попадает в техническую очередь ошибок, доступную для разбора через служебный обработчик API.

### Правила и хранение данных

A03–A06 получают данные через A08, передают их в A07 и используют возвращённое решение. Например, A05 передаёт результат поединка и состояние зависимых поединков; A07 возвращает допустимое изменение либо причину отказа. Затем A05 сохраняет результат, продвижение спортсмена, версию и аудит через A08.

A07 содержит код предметных правил и объекты, необходимые для проверки. Постоянные данные находятся в C05. Пунктирные стрелки от A07 показывают возврат результата вызова; A07 самостоятельно не запускает прикладные сценарии и не обращается к БД.

Все SQL-запросы одной UnitOfWork выполняются на одном выделенном соединении `node-postgres`. Если зависимый поединок уже начался или завершён, автоматическое изменение исхода блокируется согласно FR-09. Повтор принятой команды не продвигает спортсмена ещё раз.

### Отправка заданий и приём результатов

A04 и A06 сохраняют задания и outbox через A08 внутри транзакции предметной операции. A10 публикует только уже зафиксированные записи. Между PostgreSQL и RabbitMQ не предполагается общей распределённой транзакции.

События исполнителей входят через A12. Для жеребьёвки A12 вызывает A04, для экспорта – A06. Координатор получает задание через A08, проверяет результат с помощью A07, а для документов также использует A11. После успешного коммита управление возвращается A12, который отправляет подтверждение брокеру.

Повтор уже принятого события завершается без повторного изменения. Результат другого содержания для завершённого задания отклоняется и фиксируется в аудите. Новая версия состава или регламента делает старое задание неактуальным; новый расчёт получает новый `job_id`, а старый помечается заменённым или отменённым.

### Доступ

Права пользователя проверяются до создания задания. Сервисам выдаются отдельные учётные данные брокера с доступом к необходимым очередям и публикациям. Сообщения проверяются по схеме и сопоставляются с сохранённым заданием.

Публичные ответы формируются по разрешённому набору полей. Контакты, документы, фактический вес и сведения представителей остаются служебными. Скачивание проходит через A06 и A11 после проверки прав в A02.

Вторая диаграмма C4-L3 раскрывает C03 и содержит 9 компонентов. Входным адаптером служит потребитель сообщений, поскольку расчёт начинается после доставки задания RabbitMQ.

### Вход и выход D09

D09 устанавливает соединение с RabbitMQ и подписывается на `draw.tasks`. Когда брокер доставляет сообщение, D09 вызывает обработчик D01 с данными задания. D01 запускает D02. Опрос турнирного API и ожидание изменения каких-либо данных внутри D09 не используются.

После расчёта D02 вызывает D08. Тот собирает сообщение результата и передаёт D09 для публикации в `job.results`. После подтверждения публикации управление возвращается к D01; он подтверждает исходное задание через D09. При разрыве канала без подтверждения задания брокер может доставить его повторно.

### Вычисление и возврат результата

D02 сохраняет снимок в D03, запускает проверку D04, построение D05, оптимизацию D06 и завершающую проверку D04. Вычислительные команды и результаты передаются сообщениями ограниченного пула `worker_threads`. D07 остаётся в управляющем цикле событий и может остановить рабочие потоки по общему сроку или при утрате канала текущей обработки.

D03 хранит только временные данные. После перезапуска новое выполнение получает исходный снимок из доставленного сообщения. Сохранение официального проекта выполняется в C02 после независимой проверки обязательных ограничений. Тяжёлая перепроверка в API выполняется до короткой завершающей транзакции; в транзакции снова проверяются задание и версия.

### Корректность и воспроизводимость

Для повторения расчёта сохраняются входной снимок, версии регламента и алгоритма, `seed`, бюджет итераций и порядок разрешения равнозначных вариантов. Используется генератор псевдослучайных чисел с явно задаваемым начальным состоянием. Истечение срока не приводит к принятию случайного промежуточного проекта.

Обязательные ограничения не допускают нарушений. Встреча одноклубников признаётся вынужденной только при наличии обоснования; иначе это неустранённый мягкий конфликт. Качество оценивается по методике NFR-02 из первой лабораторной.

### Повторы и ошибки

| Ситуация | Поведение |
|---|---|
| Исполнитель остановился до подтверждения задания | RabbitMQ может доставить неподтверждённое сообщение другому исполнителю. Общий срок не обнуляется. |
| Результат опубликован, но задание не подтверждено | Расчёт и событие могут повториться; API принимает допустимый терминальный исход задания только один раз. |
| API сохранил результат, но не успел подтвердить сообщение | Повторная доставка распознаётся по событию и заданию; предметные данные повторно не меняются. |
| Изменились состав или регламент либо начат новый расчёт | Старое задание помечается неактуальным. Его результат не применяется к новой версии или новому заданию. |
| Общий срок жеребьёвки истёк | Просроченный проект не принимается. Для документов задержка фиксируется как невыполнение NFR-03, даже если пакет подготовлен позднее. |
| Сообщение некорректно либо исчерпаны разрешённые повторы | Ошибка фиксируется; необрабатываемое сообщение направляется в техническую очередь ошибок для разбора. |

Временная ошибка отдельного выполнения не закрывает задание до исчерпания принятой политики повторов. Постоянная ошибка даёт `JobFailed`; после зафиксированного терминального исхода последующие сообщения не меняют состояние задания. Недоступность будущей аналитики не останавливает жеребьёвку, проведение поединков и формирование протоколов.
